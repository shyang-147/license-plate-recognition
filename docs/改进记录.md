## 第一轮：车牌制式与透视（①②③）

| 改动 | 文件 | 实测效果 |
|---|---|---|
| **① 8 位新能源车牌**：字符数不再按固定比例估，改成用切分结果自校准 | `matlab/segmentChars.m`、`site/src/lpr_engine.js` | 难集新能源 **0/6 → 6/6**（两版都是）；7 位普通牌不受影响 |
| **② 车牌制式后处理**：新增 `plateFormat.m` 按位限定候选字符集，细长墨迹偏向 `1` | `matlab/plateFormat.m`（新增）、`recognizeChars.m`、`lpr_engine.js` | 难集整牌 25.0% → 58.3%，字符 42.5% → 75.3%；bench 字符 87.9% → 92.1%（MATLAB）；JS 难集整牌 20.8% → 50.0% |
| **③ 透视校正**：车牌四角构成梯形时用单应变换拉正（旋转+透视一次解决） | `matlab/correctPlate.m`、`lpr_engine.js` | 斜拍样本字符级明显变好（如 pe01 `*KZP816N` → `*J39818`），但 6 张仍没有一张整牌全对 |

① 原来是 `nEst = min(8, max(6, round(span/(0.125*W))))`：车牌裁紧以后，7 位普通牌和
8 位新能源牌的 `span/W` 都在 0.87 左右，这个式子**永远算出 7**，8 位牌会被强行合并掉
一个字，整牌必错。现在改成在 6/7/8 三个候选里挑"相邻字符中心间距最均匀"的那个。

③ 只在车牌**四角明显是梯形**（上下边不等长 > 8% 或四角偏离直角 > 10°）**且车牌足够大**
（高 ≥ 32 px）时才启用，其余情况仍走原来的旋转校正：本来就正的图多插值一次只会更糊。
这道闸门是实测调出来的 —— 不加的时候，小尺寸样本（掩膜只有几十像素宽，台阶状的边界
让极值点抖一两个像素就能凑出"梯形"）会被误触发，难集整牌反而从 58.3% 掉到 50.0%。

## 第二轮：残留车牌边框（④⑤⑥）

| 改动 | 文件 | 实测效果 |
|---|---|---|
| **④ 去外框改用"外圈窄带内最长连续笔画"判据** | `matlab/segmentChars.m`、`site/src/lpr_engine.js` | 网页版 bench 字符 90.0% → **92.1%**、难集字符 90.2% → **90.8%**、整牌不变；真实照片里正确字符落进候选前二的从 1/15 涨到 4/14，但整牌仍是 0/3 |
| **⑤ 定字数先试 7 / 8**（单排车牌只有这两种制式），拟合不上再退回 6~8 | 同上 | ④ 单独上线时 real01 会被切成 6 段，⑤ 把它恢复到正确的 **8 段**；bench / 难集逐图结果完全不变 |
| **⑥ 修正真实照片集的标注** | 本地实拍样图的标注文件 | 图上实际是 `京A3454警`（白底警用车牌），原标注 `京A0000警` 是错的 |

④ 原来的判据是"连续笔画超过 `0.60*W` 的水平线 / `0.85*H` 的竖线"，对合成图够用，对真实照片会漏：
真实牌照的边框被 JPEG 与模糊**打断成几段**（实测 real01 的下边框断成 51 px 和 142 px 两段，
都短于 `0.60*W` 的核长），于是整条边框残留下来，把每个字符的墨迹包围盒从 42 行撑到 58 行，
归一化时字符被纵向压扁，模板匹配得分从 0.7 掉到 0.3。现在把水平判据放宽到 `0.35*W`
（字符最长的横画也只有约 `0.13*W`，余量充足），并限制在车牌外圈窄带内生效 ——
不限范围的话会误删"相邻字符底部对齐"的行（合成集里这类行的墨迹率最高到 `0.57*W`，
和真实的边框线分不开）。

**这一项修好了"字符被压扁"，但没有修好真实照片的识别**，原因见总览 README 的「已知限制」。

## 第三轮：车牌外框白线（⑦⑧⑨）

第二轮 ④ 只是缓解，**并没有真正解决边框残留**。这一轮定位到真正的原因并修掉了它：

| 改动 | 文件 | 实测效果 |
|---|---|---|
| **⑦ 去外框改成"按连通域删除贴边细长块"，并补上"线条状"判据** | `matlab/segmentChars.m`、`site/src/lpr_engine.js` | MATLAB bench 整牌 25.0% → **95.0%**、字符 75.0% → **99.3%**、分割 60.0% → **100%**；hard 整牌 41.7% → **66.7%**；`verify_lpr` 由 25 通过/4 失败回到 **29 通过/0 失败** |
| **⑧ 极窄墨迹段（宽高比 < 0.22）直接判为 `1`** | `matlab/recognizeChars.m`、`lpr_engine.js` | bench 整牌 85.0% → **95.0%**（修掉 `1` 被认成 `4` 的两张）；手机实拍近景里的 `1` 也由此读对 |
| **⑨ 撤回"降低特征二值化阈值"** | 同上 | 见下方"为什么撤回" |

**⑦ 真正的原因**：车牌上有一圈**白色的外框线**（不是深色边框），二值化之后它和字符一样是"白"。
它是**闭合的矩形环**，于是：

- `面积 / 最长边` ≈ 6.8 —— 长边、短边的面积都算进了分子，却只除以其中一条长边，
  比真实线宽大了一倍左右，第一版"细长 => 删掉"的判据直接漏掉；
- 它又贴着车牌外沿，于是每个字符的列区间里都混进了这条白线，墨迹包围盒从 42 行被撑到 62 行，
  `normalizeChar` 把字符纵向压扁、底部还多一条横线，匹配分整体垮掉。

而 `面积 / 周长` 对任何细线都约等于**真实线宽**（实测外框 1.26 px、汉字笔画 1.67~2.2 px），
所以判据改成"贴边 + 够长 + （`面积/最长边` ≤ 4.5 **或** `面积/周长` ≤ 1.5）"，
同时覆盖"被 JPEG 打断的下边框"（细长条）和"闭合的外框白线"（矩形环）两种形态。
副作用是 bench 分割正确率从 95% 回到 **100%**：原来左下角残留的 1 px 宽、23 px 高的边框残端
会被当成第 8 个字符。

**⑧ 极窄段判 `1`**：`normalizeChar` 的 `fill` 模式会把又窄又高的 `1` 横向拉成实心方块
（实测某段墨迹宽高比 0.132，被拉宽后对模板 `1` 只有 0.31 分，而 `8` 拿到 0.51）。
逐图实测**所有数据集里第 2 位起、宽高比 < 0.22 的段 100% 都是 `1`**（车牌上唯一的细长字符，
`I` 已被排除），所以这个区间直接判 `1`；`0.22~0.30` 之间还有新能源牌被纵向压缩后的
`D/Q/5/9/F/G`，只保留原来的 +0.06 小加分、不强制。

**⑨ 为什么撤回"降阈值"**：修好外框之后重新扫了一遍特征二值化阈值 ——

| 特征二值化阈值 | bench 整牌/字符 | hard 整牌/字符 | 真实集字符 |
|---|---|---|---|
| **0.50（采用）** | 0.850 / 0.979 | **0.667 / 0.833** | **0.045** |
| 0.45 | 0.850 / 0.979 | 0.625 / 0.828 | 0.000 |
| 0.40 | 0.850 / 0.979 | 0.583 / 0.822 | 0.000 |
| 0.35 | 0.850 / 0.979 | 0.500 / 0.805 | 0.000 |

降阈值会把所有笔画一起喂胖，`3` 变 `8`、`0` 变 `9`，hard 单调变差，所以 MATLAB 侧维持 `0.5`。
网页版相反（`0.35` 更好：hard 70.8% vs 62.5%），因为它的光照归一化与降采样更"细瘦"；
两边的取值和实测依据都写在各自代码的注释里，**不要只调一边**。
> 以上是第八轮识别侧增强**之前**扫的口径；那一轮之后两边都涨了（网页版 hard 70.8% → 79.2%、
> bench 90.0% → 95.0%），但"本文件 0.35 / MATLAB 0.5"这个结论没变，仍然**不要只调一边**。

## 第四轮：定位选优（⑩）

第三轮之后，本地 3 张真实样图仍是整牌 0/3。把定位过程逐张拆开看，失败点
**全在定位这一步**，而且三张原因各不相同（见总览 README 的「已知限制」）。
这一轮只修了其中**能确定归因、代价最小**的一个：

| 改动 | 文件 | 实测效果 |
|---|---|---|
| **⑩ 双闸门（矩形度 + 框内底色占比）从"只校验胜出者"改成"参与选优"** | `matlab/locatePlate.m`、`site/src/lpr_engine.js` | `real01` 从"未检测到车牌"变成 **`*KP22933`**（新能源 8 位里后 5 位全对）；真实集字符率 0.045 → **0.273**、字符数分割 0.667 → **1.000**；bench / images / hard **逐图完全一致，零回归** |

**⑩ 的原因**：`locatePlate` 用两路掩膜（颜色通道 + 边缘通道）各挑一个最优候选，比分数取高者，
最后才用两个闸门校验**冠军**：

- 边缘通道很容易产出一个又大又方、边缘又密的糊块（比如车身的一块暗面），靠
  `sAR/sArea/sEdge` 赢下分数，但它框内的**车牌底色占比是 0**；
- 它一旦胜出，真正通过闸门的彩色候选就被丢掉，然后它自己被闸门否掉 ——
  整张图报"未检测到车牌"，**而正确答案一直躺在候选列表里**。
- `real01` 正是这个情形：颜色掩膜的连通域里明明白白有 `[660 675 164 36]`
  （中位 H=0.41 / S=0.71，就是绿牌底色），却被那个糊块挤掉了。

现在把闸门提升成**选优的主序**：候选先比"是否通过闸门"，同档之内再比分数；两个通道之间
也按同一把尺子比。**闸门阈值一个都没动**，所以原来能过的候选还是能过、原来被否的还是被否 ——
bench 20 张 + images 3 张 + hard 24 张的**逐图结果逐字节完全没变**。

网页版同步改了同一处（`lpr_engine.js` 的 `bestRegion` 与通道选择）。在这 50 张图上它是
**严格的 no-op**（逐图 `text` 与每一位 `chars` 全部相同，实测 `identical=50 different=0`），
改它是为了保持两版逻辑一一对应。

## 第五轮：白底车牌，警用（⑪⑫⑬⑭）

第四轮之后 `real03`（京A3454警，白底警牌，车牌宽约 220 px）仍认成 `冀AP1164`
（一块**没有字**的蓝色车身）。这一轮把「白底车牌」当成一类牌型补上：

| 改动 | 文件 | 实测效果 |
|---|---|---|
| **⑪ 白底车牌通道 + 彩色闸门补「框里必须有字」** | `matlab/locatePlate.m` | `real03` 从 `冀AP1164`（无意义）变成 **`*A3453警`**：序号 `A/3/4/5` 与末位 `警` 全对，只有首位 `京`（模板排名 10/31）被置 `*`；真实集字符率 27.3% → **45.5%**（10/22）；bench / images / hard 47 张**逐图逐字节完全一致，零回归** |
| **⑫ 制式与模板补 `警挂学领使`** | `matlab/plateFormat.m`、`buildTemplates.m`、`recognizeChars.m`、`site/src/lpr_engine.js` | 7 位牌末位允许 `警`（`京A3454警`）；第 3 位起改用「普通字母 + 特殊字」候选集，普通牌候选集不变；`templates.mat` 33.7 → 48.9 KB |
| **⑬ 模板导出脚本** | `tools/export_templates.m`（新增） | 模板的唯一来源是 `templates.mat`，网页版 `site/src/templates.json` 由它导出（原有三组特征逐字节一致）；网页版 50 张图重测**严格 no-op** |
| **⑭ 闸门一致性（收尾）+ 白底误检测试** | `matlab/locatePlate.m`、白底误检测试脚本（新增，仅本地） | ① `valid` 复算补上「边缘密度」，堵住"有颜色没字"的假块（纯色蓝块对照实验：补齐前 `valid=1` 放行、补齐后 `valid=0`）；② 7 张白底干扰图（白墙/白车身/白底广告牌/蓝天白云/白墙+黑线）误检由 1/7 收到 **0/7**。两项改动后 bench/images/hard/real2 **50 张逐图逐字节不变** |

**⑪ 的原因**：白底警牌在原来两路掩膜里都很难看 ——

- 真车牌在边缘掩膜里只剩一条「白底 + 黑字」的**字符带**，**矩形度 0.48 < 0.50**，被闸门卡掉；
- 同一张图里一块**没有字的蓝色假块**（车身纯色区）靠 `底色占比 0.705` 过了闸门并胜出 ——
  它是「有颜色但没字」，真车牌是「有字但没颜色」，原来的闸门只看颜色，正好判反了。

所以给彩色闸门补了一条「**必须有成排的字**」：`框内垂直边缘密度 >= 0.02`
（实测真车牌 0.067，那块纯色假块只有 0.014）。另外新增一路**白底候选**（`whitePlateRegion`）：
候选仍来自边缘掩膜，要求「白底占比 ≥ 0.35 + 垂直边缘密度 ≥ 0.02 + 矩形度 ≥ 0.40」
三项同时成立，排序用 `白底占比 × min(1, 边缘密度/0.08) × 面积占比`。

这一路是**兜底**：只有颜色/边缘两个通道都没给出过闸门的候选时才跑，所以原来能定位到车牌的
图一张都不会变 —— 这就是 47 张零回归的原因。白底候选的 `refineBox` 阈值从 0.25 放宽到
**0.10**（掩膜只剩字符带时 0.25 会把笔画上下切掉，实测框高 55 → 66，`A/3/4/5` 全部回到第 1）。

**⑪ 的附带结论：`real01` 的框高不是瓶颈**（这一条**没有落成改动**）。
按第四轮留下的验收方向换成颜色通道那个更高的框，`沪`/`A` 确实双双进前 2，
**但后 6 位全崩**（`沪AT22RJJ`，3/8，比现状 `*KP22933` 的 5/8 更差）。
根因是**分割**：换成几何上更正确的裁剪后，车牌自带的边框线会让垂直投影连成一条
（原始投影段数从 10 段变成 **1 段**），`chooseCount` 只能靠谷底硬切，边界一偏就认错。
「框切矮」反而是当前分割算法的保护色 —— 要同时保住框高和分割，得先修分割。

**⑭ 做的两件事**（都留有实测证据）：

- **闸门一致性**：`bestRegion` 的闸门已经是三条（矩形度 + 底色占比 + 边缘密度），
  但 `locatePlate.m` 末尾"收框后再确认一次"的 `valid` 只复算了前两条 ——
  "有颜色但没字"的假块会被最后一步放行。补齐后对 50 张图**零变化**。
- **白底误检**：第一轮测出 1/7（白底中文广告牌读成 `*XTD5L16`），
  加"框里要有墨迹（相对框内背景的对比度）+ 长宽比 ≤ 3.8"两道判据后 **0/7**。
  ⚠️ 白底 + 成排黑字 + 长宽比 3 左右的牌子仍分不出来（原理性风险）。

另外顺带测出一件**第四轮遗留**的问题：纯随机噪声图在真实照片尺寸下会骗过真车牌闸门
（680×1000 八个种子 8/8 误检，三个版本的定位代码输出逐字相同）。本轮只记录、没有修 ——
第六轮把它修掉了（见下一节）。

## 第六轮：闸门补「结构证据」（⑮）

第五轮把「纯噪声图会误检」测清楚了（680×1000 八个种子 8/8），这一轮把它修掉：

| 改动 | 文件 | 实测效果 |
|---|---|---|
| **⑮ 真车牌闸门补「结构证据」`hasCharStructure`** | `matlab/locatePlate.m` | 纯噪声图 **680×1000 22/30 → 0/30**、**90×90 11/30 → 0/30**（同机同日、同样的 30 个种子）；bench / images / hard / real2 **50 张逐图逐字节不变**；`verify_lpr` 30 通过 0 失败；白底干扰集仍 0/7 |

原来那套闸门（长宽比 / 矩形度 / 底色占比 / 边缘密度）**全是「尺度无关」的统计量**：
把图放大到真实照片尺寸，随机噪声里总能凑出一块样样过关的斑块 —— 第五轮实测 8/8 报出
`*SB1S181`、`冀AZRJN9` 这类凭空捏造的车牌号。缺的是「**这是一块有字的车牌**」这种结构证据。

`hasCharStructure` 复用 `segmentChars` 前几步的二值化，然后看两件事：

1. **墨迹不能是一整坨**：最大墨迹连通域占框内像素的比例 ≤ 0.25。
   实测纯噪声 / 纯色块二值化后墨迹连成一整块（0.27~0.48），真车牌则是十来个字符块（0.035~0.14）。
2. **字符带内切得出 2~12 段**：先去掉「贯穿整行」的边框亮线（车牌自带的白边会把字缝填平），
   再在字符带里做列投影，阈值取**该列墨迹量的相对值**（0.25×峰值）。
   实测真车牌 2~9 段；纯噪声因为每列墨迹量几乎相同、列投影是一整条，恒为 1 段。

**两个设计决策**（都很容易踩反，代码注释里也写了）：

- **只做否决、不参与 `bestRegion` 的选优。** 它衡量的是「这个框喂给分割会不会切出字」，
  必须在 `refineBox` 收紧后的最终框上算；在候选连通域的原框上算会把小号牌（车牌只占框的
  一部分）误判成「切不出字」。实测把它挪进选优会大面积误杀：bench 掉到 0.75、hard 掉到
  0.458、real01 从对 5 位变 0 位。
- **段数下限取 2 而不是 6~9。** 实测小结牌（120~170 px 宽）本来就糊成一两段，卡 6 段会把它们
  全挡掉；真正有判别力的是「1 段 = 一整坨」。

它证明的只是「框里有成排的墨迹」，**不等于**「这是车牌」—— 蓝底广告牌、白底大字标牌一样能过，
那是本工程已知的原理性限制。

**`real01` 的分割问题这一轮查清了，但没有落成改动**（结论与证据见
`评审与改进/第六轮_技术报告.md`）。

**网页版一行都没动**：用 `测试脚本/noise_fp_js.mjs` 实测，网页版引擎在同样两个尺寸的纯噪声图上
**30/30 本来就全部正确返回「未检测到车牌」**。两边边缘通道不等价（MATLAB 用 `edge` 的自动阈值、
网页版用自写的梯度均值阈值），这类常数不能照搬，**不要为了「对称」给网页版加结构证据**。

## 第七轮：真实集扩容 + 小目标退化集（⑯⑰⑱，C 项）

这一轮**不改识别逻辑**，补的是「能下判断的数据和口径」——
`lpr_main.m` / `locatePlate.m` / `segmentChars.m` / `recognizeChars.m` 一行未改。

**⑯ 真值车牌框。** 所有标注补了 `bx,by,bw,bh`（**纯数字四列**）。定位阶段第一次可以独立判命中
（IoU ≥ 0.5），不再靠「切出了字符就默认定位没问题」。3 张真图的框是按色掩膜 + 连通域量的；
`real03` 白底牌与白车身同色（色掩膜会把保险杠框进来，长宽比 5.18 明显错），改用第五轮报告里
记录的框换算回原图，再叠图目视核对。来历与精度写在 `测试数据/real2/README.md`。

> ⚠️ 一开始写成 `"x y w h"` 这种**带空格的引号字段**，MATLAB `readtable` 的自动分隔符猜测会被
> 字段里的空格带偏，整张表读成 `Var1..Var4`，`T.file` 直接报错。改成四列纯数字才稳。

**⑰ 两组退化集。**
- 合成小目标 `测试数据/degrade/`（60 张 = 车牌宽 220→38 px 十档 × 6 张）：先按 440×140 原生尺寸
  渲染**再降采样**（直接用小字号渲染，边缘仍是矢量级清晰，比真实照片乐观太多），外加定像素
  高斯模糊 + JPEG。**每档用同一批车牌**，档与档的差只剩宽度。
- 真实照片降采样 `测试数据/degrade_real/`（18 张 = 3 图 × 6 档）：整图 LANCZOS，真值框同步缩放。
  只能模拟分辨率损失，模拟不了运动模糊 / 曝光变化，是**下限估计**，不能当真实曲线读。

**⑱ 阶段归因评测 `matlab/bench_stage.m`。** 与 `bench_eval.m` 并存、用途不同：`bench_eval` 只回答
「整牌对不对」（历史口径，`run_all.m` 在用），`bench_stage` 把每张图归因到**唯一一个阶段**
（正确 / 定位失败 / 分割失败 / 识别失败），并**按 `category` 分组**。顺带修了分组统计的分母 bug：
没检测到框的图（IoU = NaN）被排除出定位分母，`w048` 明明 6 张里 3 张没框，分组表却写「定位 100%」，
和同一行的「定位失败 3」自相矛盾。

**实测（合成退化集 60 张，`bench_stage` 逐档归因）：**

| 车牌宽 | 220 | 180 | 150 | 125 | 105 | 90 | 75 | 60 | 48 | 38 |
|---|---|---|---|---|---|---|---|---|---|---|
| 整牌 | **100%** | 66.7% | 16.7% | 16.7% | 16.7% | 0 | 0 | 0 | 0 | 0 |
| 字符 | **100%** | 95.5% | 84.1% | 75.0% | 70.5% | 27.3% | 9.1% | 0 | 4.5% | 4.5% |
| 定位(IoU≥.5) | 100% | 100% | 100% | 100% | 100% | 100% | 100% | 83.3% | 83.3% | 83.3% |

**先崩识别**（180 px 字符率就开始掉，100% → 95.5%）、**再崩分割**（90~75 px 接棒）、
**定位最后倒**（60 px 以上一直是 100%）。这条顺序决定了下一步该做**识别侧**的低分辨率增强
（双三次上采样 + 锐化 / 逐字符局部阈值 / 灰度相关代替二值 IoU），而不是定位。

**3 张真图的账第一次看清**：定位 **3/3 全中**（IoU 0.655 / 0.836 / 0.774），**没有一张是定位错位**；
三张的失败都在识别 / 分割边界（`real01`、`real03` 的定位框高只有真值的 0.72 / 0.79 倍，
绿牌/白牌底边被切、上下沿笔画被削）。

**闸门取证 `测试脚本/probe_gate_gt.m`**：对每张图同时跑「整图选中的框」与「真值框外扩 70% 的裁片」，
两列并排才能分清「没被选中」和「过不了闸门」。结论和直觉相反 —— 低分辨率下被否掉的框
**大多压根不在车牌上**（IoU = 0.000），真车牌在裁片里明明是好的，所以账该记在
「候选没被选中」上，不是「闸门擦边」。真车牌自己过不了闸门只发生在最小两档
（`real01` ≤ 53 px、`real02` ≤ 36 px）。另有一处**闸门放行错块**：`real03_s032` 选中的框
valid、底色占比 0.86、IoU = 0.000 —— 小尺度下「底色占比」这条判据失去鉴别力
（已知限制，本轮不修）。

**零回归**：`verify_lpr` 30 通过 0 失败；纯噪声误检 0/8、0/8；
bench / images / hard / real2 四集逐图结果与第六轮归档 **SHA256 完全相同**。

**没有做的那半**：真实照片仍然只有 3 张 —— 这个脚本变不出来，得真去拍。不过标注格式、
归因口径、复现脚本都已就位，拍回来直接灌进来就行。

**网页版一行都没动**：退化集评测走的是 MATLAB 侧的 `bench_stage`，网页版引擎没有对应改动。

第七轮把退化曲线留在了「**先崩识别**（180 px 字符率就开始掉）、再崩分割、定位最后倒」，

### ㉓ CCPD 真实照片集（C 项最后一块）

「15~30 张真实照片」这个缺口，脚本变不出来 —— 但公开数据集可以。选了 **CCPD**
（`detectRecog/CCPD`，**MIT 许可**）：文件名里自带 8 点四角 + 车牌号 + 面积/亮度/模糊度，
30 万张，还按难度分好了 subset；其中的 `ccpd_np` 是**真实但没有车牌**的照片，
正好补上「误检只能在纯噪声图上测」的缺口。

**取数只花了约 24 MB**：整包含 1.5 GB，但 **zip 的中央目录在文件末尾** ——
用 HTTP Range 只读末尾几十 KB 的中央目录，挑好条目后再按 `header_offset` 把相邻条目
合并成 ≤4 MB 的请求，手工 `zlib.decompress(raw, -15)`。360 张共 **186 次 Range 请求**
（`项目代码/tools/fetch_ccpd_sample.py`）。

> ⚠️ **坑：文件名第 2 段的 `rect` 不是车牌框。** 一开始按直觉把它当 `bbox` 用，
> 结果**整体偏上、框到车标去了**（皖S69016 那张：rect `[385 430 83 53]` vs 四角外接框
> `[384 440 89 47]` vs 车牌蓝色像素实测 `[377 440 95 47]`）。第 4 段的**四角**才是车牌。
> 另外少数图的**顶点顺序是乱的**（320 张里 16 张对边不等），不重排会让多边形自交、面积算错。

> ⚠️ **坑：外接框 IoU 的上限只有 0.776。** 四角是**旋转**矩形，它的轴对齐外接框会把背景
> 框进来 —— 拿外接框当真值，`IoU>=0.5` 这条线连「完美轴对齐检测器」自己都过不了
> （320 张里 45 张 = 14.1% 如此；`ccpd_tilt` 组上限中位只有 0.486）。所以新增
> `matlab/quadIoU.m`，真值侧改用**多边形** IoU（凸多边形 × 半平面裁剪，参数插值 `t = sa/(sa-sb)` 是精确的）。

### ㉒ 负样本口径

`ccpd_np` 的文件名里没有标注串，`text` 是空的。直接塞进 `bench_stage` 会出事：
「什么都没检出」时 `strcmp(got, gt)` 判成**整牌正确**，40 张无牌图能把整牌率凭空抬高 10 个点，
而且它们还会混进定位/分割的分母。新口径：**`text` 空且没有有效真值框 = 这张图本来就没有车牌**，
不进四个分母，单独统计拒识/误检；逐图归因多一格「误检(无车牌图)」（只在有负样本时出现，
老集合的输出逐字节不变）。顺带一个 MATLAB 的坑：`if S.isNeg`（逻辑**向量**）只在**全真**时才成立，
逐图累加 `S.isNeg` 会让这个分支永远不走 —— 必须先赋给标量再判。

图像处理能直接改的，上 CNN 反而会把「哪一步错了」这个已经算清楚的问题重新糊掉。

`ml_s8_*` / `ml_s8b_*` 四份 SHA256 完全相同；与第六轮归档逐图比对 bench / images

## 第九轮：定位闸门与真实域取证（㉔，C 项）

第八轮把真实照片集（CCPD 320 + 40）建起来之后，账面上躺着两条最刺眼的数字：
**定位 35.3%**、**无牌图误检 57.5%**。这一轮先给它们做取证，再决定动不动手 ——
结果是**只动了一处**，另外两处被自己的数据证伪。

| 改动 | 文件 | 实测效果 |
|---|---|---|
| **㉔ 白底通道补「结构证据」**：白底候选除了「白底占比 + 垂直边缘密度」，还要 `hasCharStructure` 通过（与彩色通道同一条，仍**只做否决、不参与选优**） | `matlab/locatePlate.m` | 真实无牌照片 `ccpd_np` 误检 **23/40 → 15/40**（其中白底通道 10 → 2）；CCPD 正样本定位 **113/320 不变**；`verify_lpr` 30 通过 0 失败；纯噪声 0/8、白底干扰 0/7 |

**为什么是白底通道**（路线图 P0-2 说的恰好相反：「白底通道不要动」）：
把 40 张真实无牌照片的 23 个误检**按通道拆开**才发现，**白底通道放行了 10 个**，
只比彩色通道少 2 个。而白底通道那个「0/7」是第五轮拿 **7 张合成干扰图**验收的 ——
里面没有一张是汽车照片，这条通道的真实风险被系统性低估了。

补上结构证据后挡掉 **8/10** 个白底误检，而代价实测为 **0**：
320 张正样本里靠白底通道拿到框的 20 张只有 2 个是定位命中，
被结构证据否掉的 10 张里**一个命中都没有**，所以定位命中仍是 113/320。

**「两侧一起量」是这一轮的方法论要点**：只量负样本会得出「越严越好」的结论，
必须同时对正样本量代价（`测试脚本/probe_white_gate.m`，改动前后的数字都留在
`结果记录/probe_white_gate_第九轮*.txt`）。同理**没有**去调 `minWhiteFr`
（0.35 → 0.489 能挡掉 10/10 个白底误检，但会否掉 4 张正样本白底候选，
而且这个阈值是照着 40 张负样本反推的，撑不住）——结构证据是**有物理含义**的判据，
不是拟合出来的阈值。

### 被证伪的三条（都没落成改动）

- **P0-1 局部 / 自适应二值化**：A/B 显示全面变差 —— 定位命中后的字符率
  clahe **15.3%** vs adaptive 4.3% / 8.0%、Sauvola 7.2%、逐字符阈值 12.2%。
  而且**「字符数切对」反而略微上升（55.8% → 57.5%）**，掉的**全是逐位识别**：
  局部二值化让分割更方便，却把笔画弄糊，模板匹配直接崩。
  这条**推翻了第八轮「窄到 90 px 以下的瓶颈在分割」的判断** —— 瓶颈在识别。
- **P0-2 彩色通道加颜色正向证据**：真车牌与误检块的判据分布**几乎完全重叠**
  （单维最优也只能挡住 5/13；组合规则最好挡 8/13 却要赔 15.5% 的真车牌），
  在**检测器真正交出的框**上代价更大（`aspect<=3.4` 会砍掉 46% 的命中）。
  路线图那条「误检 ≤ 6/40 且定位不低于 0.353」在这个约束下**无解**。
- **结构证据判据本身也不动**：真实流程里被它否掉的 40 张中，**本身框是对的只有 2 张**，
  而放松判据（V2）会把 24 张改成否决 —— 收益上限 2、代价 24，不划算。
